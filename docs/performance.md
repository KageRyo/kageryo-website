# 正式站效能基準

本文件記錄 `38755557604f3bc6befa19b43d3da0d382658ca6` 部署版本的 Lighthouse 實驗室量測；該版本的 [GitHub Pages 部署工作](https://github.com/KageRyo/kageryo-website/actions/runs/38128939103) 於 2026-10-11 成功完成。量測對象是 `https://kageryo.coderyo.com` 的繁體中文預設頁面，沒有將本機開發伺服器或目前工作分支的結果混入。數值是當時裝置、網路與第三方資源狀態下的樣本，不能代表真實訪客的 Core Web Vitals 或 INP。

## 方法與環境

- 工具：Lighthouse CLI 13.5.0、Google Chrome for Testing 151.0.7922.34、Node.js 24.19.0（`mise exec --`）。環境：Linux 6.18.33.2-microsoft-standard-WSL2、Intel Core i7-12700KF、20 個邏輯 CPU。
- 每個路由的手機與桌面 profile 各順序執行三次，使用獨立 Chrome 暫存 profile 與 Lighthouse 預設儲存空間清除；量測期間不並行執行本機 build 或瀏覽器壓力測試。WSL 的 Chrome launcher 會從 Windows PATH 推導暫存目錄，因此後續測次在忽略目錄內執行，避免它把暫存 profile 建在 repository 根目錄。
- 手機：412 × 823、DPR 1.75、模擬 RTT 150 ms、throughput 1638.4 Kbps、CPU slowdown 4×。桌面：1350 × 940、DPR 1、模擬 RTT 40 ms、throughput 10240 Kbps、CPU slowdown 1×。兩者皆使用 `simulate` 節流；分數因 profile 與評分曲線不同，不直接當作同等工作負載比較。
- Performance、FCP、LCP、TBT、CLS、Speed Index 與 total-byte-weight 均從 Lighthouse JSON 的 `score` 或 `numericValue` 擷取，先對未四捨五入的原值分別取中位數，再格式化顯示。各欄的中位數不保證來自同一測次。total-byte-weight 是量測期間擷取到的資源大小，不是首屏傳輸量。
- 完整 JSON 與 HTML 報告保存在本機忽略目錄 `.claude/codex-project-plans/performance/`，檔名為 `{route}-{mobile|desktop}-{1|2|3}.report.{json|html}`。`route` 依序為 `home`、`about`、`projects`、`contact`、`kserve`、`tag-twin`。報告不進版控。

重現範例（其他路由替換 URL、檔名；桌面加 `--preset=desktop`）：

```bash
mkdir -p .claude/codex-project-plans/performance
(
  cd .claude/codex-project-plans/performance
  env -u LOCALAPPDATA -u APPDATA LD_LIBRARY_PATH=/home/ryo/.cache/pw-libs/root/usr/lib/x86_64-linux-gnu CHROME_PATH=/home/ryo/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome mise exec -- npm exec --yes --package=lighthouse@13.5.0 -- lighthouse https://kageryo.coderyo.com/about --only-categories=performance --output=json --output=html --output-path=about-mobile-1 --chrome-flags='--headless --no-sandbox' --quiet
)
```

`LD_LIBRARY_PATH` 與 `CHROME_PATH` 是這部 WSL 主機的安裝位置；其他主機要換成對應路徑。清除繼承的 `LOCALAPPDATA`／`APPDATA`，並在忽略目錄內執行，可限制 Chrome 暫存 profile 的落點。每次改用新的 output path，保存完整報告。Lighthouse 的[效能評分說明](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring)與[命令列使用說明](https://developer.chrome.com/docs/lighthouse/overview/)可供解讀分數與重現方式。

## 其他驗證與解讀

另以正式站首頁的全新瀏覽器 context 驗證語言切換：起始選項為 `zh-TW`，首次切到 `en` 才請求 `/assets/en-BI7UGhcN.js`，首次切到 `ja` 才請求 `/assets/ja-BJouwaa8.js`，兩個請求皆為 HTTP 200 且沒有頁面 JavaScript 錯誤。這是互動及延遲載入驗證，沒有併入冷啟動效能表格。

本輪沒有取得 PageSpeed Insights／CrUX 的真實訪客資料，故 INP、訪客 LCP 與訪客 CLS 均標為「無資料」。本表的 LCP、CLS 和 TBT 是 Lighthouse 實驗室結果；TBT 也不等於 INP。網路、第三方資源與主機負載都可能造成分數變動，例如首頁桌面 57–81、KServe 桌面 58–95。評估後續修改應以相同部署對照方式及多次量測檢查，而不是只比較單次分數。

`/projects/federated-aqi` 與 `/projects/environmental-enforcement` 在此部署 SHA 尚未上線，因此沒有正式站基準；待它們各自部署後，需記錄新部署 SHA 並按相同手機／桌面各三次流程追加報告，不能把目前的主路由結果套到新詳情頁。

## 後續改善優先順序

1. **檢查阻擋渲染的字型與 Tocas 資源。** `home-mobile-1` 的 `render-blocking-insight` 列出 Google Fonts 的 Noto Sans TC CSS、Tocas 5.7 CSS／JS 與本站 CSS；其他路由也反覆出現 Google Fonts 與 Tocas。首頁手機 LCP 中位數 8.02 秒，About 手機為 14.11 秒。先確認 Tocas 初始化依賴、三語 glyph 與字重，再做單一改動並重測 FCP／LCP；診斷中的「估算節省時間」不是已實現成果。[Chrome 的阻擋渲染說明](https://developer.chrome.com/docs/performance/insights/render-blocking)提供分析方法。
2. **追查 About 與 Projects 的版面位移。** About 手機三次 CLS 為 0.3069–0.3073，Projects 手機為 0.1600–0.1603、桌面為 0.2088–0.2113，波動小且值得先定位。`about-mobile-2` 的 `layout-shifts` 指向個人簡介主欄，`projects-mobile-2` 指向 KServe 專案卡片內容；這些是移動的元素，不足以單獨認定觸發原因。應用時間軸與實際畫面確認字型、非同步內容或尺寸預留的影響後再修改。[Chrome 的 CLS 原因分析說明](https://developer.chrome.com/docs/performance/insights/cls-culprit)可供追查。
3. **核對圖片在各版面的顯示尺寸與下載量。** `home-mobile-1` 的 `image-delivery-insight` 指出品牌插畫 1600 × 900 在當次僅顯示 382 × 215，About 個人照和 Projects 卡片圖片也列在診斷中。首頁手機傳輸量中位數 2,385,255 B，Projects 手機為 2,083,157 B；這是整個擷取期間的資源量。先確認候選圖片是否在可見區、是否影響該頁 LCP，才評估響應式圖檔；首頁手機的 LCP 主要是介紹文字，不能只憑圖片診斷宣稱縮圖會改善它。圖片調整仍需保留目前照片、輪播與去除 EXIF／GPS 的資產規則。

每項改善各自開 PR。部署後用相同 Lighthouse／Chrome、profile、冷快取與三次取樣，比較 FCP、LCP、TBT、CLS、Speed Index 及傳輸量；保留 UI、三語、輪播控制、圖示與可讀字型的回歸檢查。
