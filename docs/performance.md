# 正式站效能基準

本文件記錄 `ce7602adbfd45d0911c0cf9877a0b9bcd549a67b` 部署版本的 Lighthouse 實驗室量測；該版本的 [GitHub Pages 部署工作](https://github.com/KageRyo/kageryo-website/actions/runs/43815881421) 於 2026-11-16 成功完成。量測對象是 `https://kageryo.coderyo.com` 的 8 個路由，繁體中文和英文頁面各量一輪。數值是當時裝置、網路與第三方資源狀態下的樣本，不能代表真實訪客的 Core Web Vitals 或 INP。

上一版基準是 2026-10-11 的部署版本 `38755557604f3bc6befa19b43d3da0d382658ca6`，量了 6 個路由的繁體中文頁面。下面的前後比較都只用繁體中文這一輪。

## 方法與環境

- 工具：Lighthouse CLI 13.5.0、Google Chrome for Testing 151（Playwright 的 `chromium-1234`）、Node.js 24.22.1（`mise exec --`）。環境：Linux 6.18.33.2-microsoft-standard-WSL2、Intel Core i7-12700KF、20 個邏輯 CPU，和上一版是同一部主機。
- 語言：Lighthouse 啟動的 Chrome 語言是 `en-US`，網站依首次造訪的語言規則會顯示英文。繁體中文那一輪另外設定 `LANG=zh_TW.UTF-8`、`LANGUAGE=zh_TW`，並加上 `--lang=zh-TW --accept-lang=zh-TW`；只加 `--lang` 時，headless Chrome 仍顯示英文。48 份中文報告都確認過頁面文字是中文。
- 每個路由的手機與桌面 profile 各順序執行三次，使用獨立的 Chrome 暫存 profile，並沿用 Lighthouse 預設的儲存空間清除。中文那一輪期間沒有執行本機 build 或測試；英文那一輪期間跑過幾秒鐘的單元測試與字型計算腳本，可能讓少數測次的 TBT 偏高。WSL 的 Chrome launcher 會從 Windows PATH 推導暫存目錄，所以要在忽略目錄內執行，避免暫存 profile 建在 repository 根目錄。
- 手機：412 × 823、DPR 1.75、模擬 RTT 150 ms、throughput 1638.4 Kbps、CPU slowdown 4×。桌面：1350 × 940、DPR 1、模擬 RTT 40 ms、throughput 10240 Kbps、CPU slowdown 1×。兩者皆使用 `simulate` 節流；兩種 profile 的評分曲線不同，分數不直接互相比較。
- Performance、FCP、LCP、TBT、CLS、Speed Index 與 total-byte-weight 均從 Lighthouse JSON 的 `score` 或 `numericValue` 擷取，先對未四捨五入的原值分別取中位數，再格式化顯示。各欄的中位數不一定來自同一測次。total-byte-weight 是量測期間擷取到的資源大小，不是首屏傳輸量。
- 完整 JSON 與 HTML 報告保存在本機忽略目錄：英文在 `.claude/codex-project-plans/performance-2026-11-16/`，繁體中文在其下的 `zh/`。檔名為 `{route}-{mobile|desktop}-{1|2|3}.report.{json|html}`，`route` 依序為 `home`、`about`、`projects`、`contact`、`kserve`、`tag-twin`、`federated-aqi`、`environmental-enforcement`。報告不進版控。

重現範例（繁體中文；英文拿掉 `LANG`、`LANGUAGE` 與兩個語言旗標；其他路由替換 URL 和檔名；桌面加 `--preset=desktop`）：

```bash
mkdir -p .claude/codex-project-plans/performance-2026-11-16/zh
(
  cd .claude/codex-project-plans/performance-2026-11-16/zh
  env -u LOCALAPPDATA -u APPDATA LANG=zh_TW.UTF-8 LANGUAGE=zh_TW LD_LIBRARY_PATH=/home/ryo/.cache/pw-libs/root/usr/lib/x86_64-linux-gnu CHROME_PATH=/home/ryo/.cache/ms-playwright/chromium-1234/chrome-linux64/chrome mise exec -- npm exec --yes --package=lighthouse@13.5.0 -- lighthouse https://kageryo.coderyo.com/about --only-categories=performance --output=json --output=html --output-path=about-mobile-1 --chrome-flags='--headless --no-sandbox --lang=zh-TW --accept-lang=zh-TW' --quiet
)
```

`LD_LIBRARY_PATH` 與 `CHROME_PATH` 是這部 WSL 主機的安裝位置，其他主機要換成對應路徑。清除繼承的 `LOCALAPPDATA`／`APPDATA` 並在忽略目錄內執行，可以控制 Chrome 暫存 profile 的位置。每次改用新的 output path，保存完整報告。解讀分數與重現方式可參考 Lighthouse 的[效能評分說明](https://developer.chrome.com/docs/lighthouse/performance/performance-scoring)與[命令列使用說明](https://developer.chrome.com/docs/lighthouse/overview/)。

## 其他驗證與解讀

**版面位移的原因。** Lighthouse 的位移來源和瀏覽器的 `layout-shift` 記錄指出三個原因：Noto Sans TC 換上時文字重新換行（Lighthouse 標為 Web font loaded）；`.ts-image` 是 `inline-block`，圖片載入前寬度為 0，宣告的 `width`／`height` 保留不到空間；頁面元件是延遲載入的，元件到之前頁尾先出現在畫面底部，之後被內容推下去。[#155](https://github.com/KageRyo/kageryo-website/pull/155) 修正這三點。本機以 `vite preview` 對照英文頁手機版，三次中位數：作品集 CLS 0.1585 → 0、About 0.0587 → 0、環保科技執法 0.0587 → 0（三次中最高 0.0080）。「量測結果」與「與 2026-10-11 比較」兩節是修正前的數字，部署後的結果在上一節。

**字型是最大的傳輸量。** 中文頁手機版每頁下載 12–23 個 Noto Sans TC 分割檔，約 0.6–1.3 MiB；手機各測次中，字型占整頁傳輸量的 55–84%。英文頁因為姓名、校名等中文字，也會下載 5–19 個分割檔。中文頁手機的 LCP 明顯比英文頁慢（首頁 6.29 秒對 4.31 秒、KServe 7.85 秒對 3.77 秒），兩邊的 LCP 元素都是文字。字型與 JS、CSS 搶頻寬是可能的原因，但還沒用時間軸確認。

**實驗室數字的限制。** 這輪沒有 PageSpeed Insights／CrUX 的真實訪客資料，INP、訪客 LCP 與訪客 CLS 都是「無資料」。表中的 LCP、CLS 和 TBT 是實驗室結果，TBT 也不等於 INP。同一路由三次之間的差距可能很大，例如中文 KServe 手機 LCP 6.01–8.56 秒，評估修改時要用相同流程量多次再比較。

## 後續改善優先順序

1. **減少 Noto Sans TC 的下載量。** 目前載入 400–700 的可變字重，中文頁每頁要下載 0.6–1.3 MiB 字型，文字的 LCP 也常跟著最後一個字型檔載完的時間走。可以評估只載入實際用到的字重，或比照圖示字型的做法，自行託管只含網站用字的子集；GitHub 專案描述這類動態文字不在子集內，要保留備用字型。每個做法都要重量 LCP 與傳輸量再決定，並確認三語的字形都正確。
2. **確認中文 About 與聯絡頁手機 LCP 上升的原因。** 用 Chrome 效能面板錄時間軸，對照 LCP 候選元素的出現時間和 Noto Sans TC 的載入時間，確認是不是換字型時重新算 LCP；查清楚之前，不要為了 LCP 數字調大備用字型，以免又出現換行造成的版面位移。作品集手機版的 LCP 元素已經從摘要文字變成第一張卡片圖片，比較前後數字時要先確認 LCP 元素相同。
3. **阻擋渲染的資源。** 所有路由的 `render-blocking-insight` 都列出 Google Fonts 的 Noto Sans TC CSS、Tocas 5.7 CSS 與本站 CSS。調整前先確認 Tocas 的初始化依賴，一次只改一項並重測 FCP／LCP；診斷中的「估算節省時間」不是實際成果。分析方法可參考 [Chrome 的阻擋渲染說明](https://developer.chrome.com/docs/performance/insights/render-blocking)。

每項改善各自開 PR。部署後用相同的 Lighthouse／Chrome、profile、冷快取與三次取樣，比較 FCP、LCP、TBT、CLS、Speed Index 及傳輸量，並保留 UI、三語、輪播控制、圖示與字型可讀性的回歸檢查。
